# Pure-Rust cache benchmark, October 2026

Question (spec §14): for a cargo-only repository, which cache works best: Swatinem/rust-cache,
sccache on the GitHub cache, sccache on R2, or no cache? Should hoard serve a protocol that
sccache speaks?

Setup (2026-10-23): `ubuntu-latest` (4 vCPU), Rust 1.97, `CARGO_INCREMENTAL=0`, sccache 0.18.0,
rust-cache 2.9.3 (`@v2`). Sample repos, read-only checkouts of `main`:
[keelstackhq/bosun](https://github.com/keelstackhq/bosun) (132 crates in `Cargo.lock`; 198
cacheable rustc/cc calls, 98 not cacheable) and
[keelstackhq/berth](https://github.com/keelstackhq/berth) (73 crates; 115 cacheable, 76 not).
Each job runs `cargo test --locked --no-run`, then `cargo clippy --all-targets --locked`.
`cold` starts with an empty cache. `warm` runs on a fresh runner after a one-line change to the
repo's own crate, like an agent PR on a warm `main`. Each run uses its own cache keys.

## Warm job (the PR case), seconds of test-build + clippy

| repo | no cache | rust-cache | sccache, GitHub cache | sccache, R2 |
| --- | --- | --- | --- | --- |
| bosun | 28.7 / 46.4 / 47.6 | **19.7** (+3 restore, 134 MB) | 37.9 (99.5% hits) | 55.9 / 56.9 / 64.1 (99.5% hits) |
| berth | 17.8 / 26.6 | **7.0** / **8.8** (+2–6 restore, 91–108 MB) | — | 26.1 / 32.9 (99.1% hits) |

## Cold job, seconds of test-build + clippy

| repo | no cache | sccache, GitHub cache | sccache, R2 |
| --- | --- | --- | --- |
| bosun | 32.1 / 51.0 | 50.3 | 80.9 / 80.9 |
| berth | 16.8 / 19.7 | — | 45.9 / 48.8 |

rust-cache's cold job is the no-cache build plus a 2–5 s save step.

## GitHub cache upload limit (sccache)

sccache writes one GitHub cache entry per compiled crate: a cold bosun job is 198 uploads in
about 50 s, close to the 200 uploads/min per-repository limit on its own.

- One cold job alone: 0 of 198 writes failed; the next warm job hit 197 of 198.
- 5 parallel cold jobs (like bosun's 5-gate CI matrix): 157, 122, 99, 109 and 147 of 198
  writes per job failed with `RateLimited` (HTTP 429 on `CreateCacheEntry`), 634 of 990 in all.
  The builds stay green, so nothing shows the loss; a warm job after such a run hit 19%.
- sccache's documented setup (`docs/GHA.md`: export `ACTIONS_RESULTS_URL` and
  `ACTIONS_RUNTIME_TOKEN`) without `ACTIONS_CACHE_SERVICE_V2=on`: 198 of 198 writes failed, alone,
  with no other uploads. The build is green and the cache stays empty.

## Local check (4-core container, bosun, test-build only)

cold 37.8 s; warm `target/` with the crate touched 15.9 s; sccache on local disk 17.1 s (120 of
120 cacheable calls hit, 79 MB). sccache 0.18 also caches clippy's metadata-only builds
(clippy 18 s cold → 11 s warm), although its `docs/Rust.md` says `link` must be in `--emit`.

## Runs

Workflows `rust-bench.yml` and `rust-bench-burst.yml` on branch `claude/rust-cache-research`
(commit 5173b15):

- clean bench (2 repeats, rust-cache keys fixed): https://github.com/keelstackhq/hoard/actions/runs/39969545861
- sccache on the GitHub cache alone, cold → warm → documented setup: https://github.com/keelstackhq/hoard/actions/runs/39969545941
- 5 parallel cold sccache jobs: https://github.com/keelstackhq/hoard/actions/runs/39968589984
- first bench (no-cache and sccache-R2 numbers; sccache-gha legs ran with the burst):
  https://github.com/keelstackhq/hoard/actions/runs/39968590111

Notes:

- Runner speed varies a lot (bosun no-cache warm: 28.7 s to 47.6 s), so the table shows every
  sample. rust-cache was faster than every no-cache sample on both repos.
- The rust-cache keys in the clean run did not include the repo, so two jobs restored the
  other repo's cache by prefix (`full match: false`). The table shows only the jobs that restored
  their own cache (`full match: true`). bosun's warm job with berth's cache took 28.5 s.
- The sccache R2 objects are under `cache/sccache-bench/` in the test bucket, so hoard's
  lifecycle rule (7 days) and size cap remove them.
- Missing R2 credentials make sccache fail `cargo` (exit 101): a storage setup error fails the
  build.
